# 代码与性能复查

日期：2026-10-15。基线为 `f744f83`；本机 Node 与 Chrome 测量，不代表手机、Safari 或 GPU 帧率。

## 本次优化

- 显示层按不可变快照的身份判断是否需要同步。高刷新率下没有新的模拟步、下蛋等状态变化时，复用当前显示；特效 Tween 仍独立运行。暂停换皮肤和窗口缩放明确强制刷新，避免同一快照被错误跳过。
- 鸡、蛋显示对象使用同步序号标记存活状态，不再每次同步创建三组 ID 数组与 Set。遍历后清理未出现的对象，蛋静止时也会先更新存活标记。
- 批量预留蛋位时在原数组内压缩剩余候选，避免每预留一颗蛋创建一个新数组；候选顺序、最近位置、间距和部分批次规则不变。独立计时的收益很小，这项主要减少短命数组，不能据此宣称下蛋算法有显著加速。
- 删除场景创建时紧接布局的一次重复同步。

## 测量

浏览器采用 1920 × 1080、正常规则预热 90 个游戏秒，再模拟 12 秒的 60/144 Hz 刷新节奏。每 13/60 秒请求下蛋，包含场景更新、Tween 和深度排序，不包含逐帧 GPU 绘制；不是实际 144 Hz 显示器帧率测试。

| 指标 | 优化前 | 优化后 |
| --- | ---: | ---: |
| 60 Hz 段 CPU 总耗时 | 633 ms | 640 ms |
| 60 Hz 单次 CPU P95 | 1.2 ms | 1.2 ms |
| 144 Hz 段 CPU 总耗时 | 958 ms | 617 ms |
| 144 Hz 单次 CPU P95 | 0.9 ms | 0.9 ms |
| 144 Hz 实际角色同步次数 | 1,729 | 765 |
| 144 Hz 深度排序次数 | 1,729 | 992 |

高刷新率段减少约 36% 的场景 CPU 时间；普通 60 Hz 段基本持平。144 Hz 下有 964 次调用复用了同一份快照；独立特效和新建对象仍可能触发深度排序。两组前后得分与最终实体数量一致。

纯模拟基准使用种子 123，60 Hz 推进 180 秒，每 13 步下蛋。可运行 `npm run benchmark`；用 `GAME_SOURCE_ROOT` 指向基线副本进行对照。额外验证了 3840 × 2160。原版与优化版交替执行三次，1280 × 720 和 3840 × 2160 的完整最终快照 SHA-256 各自完全一致，涵盖位置、年龄、姿态、分数、小猪和泥坑状态。

初次基线采样的下蛋 P95 分别为：1280 × 720 约 0.25 ms，1920 × 1080 约 0.52 ms，3840 × 2160 约 2.56 ms。交替对照中，候选数组优化后的 P95 与基线接近，未观察到显著的算法耗时下降。

## 后续优先级

1. **大窗口实体密度。** 当前视觉缩放上限为 1，屏幕变大后角色尺寸不再增长，蛋位和鸡群数量继续增加。180 秒基准的实体峰值从 1080p 的 2,685 增长到 4K 的 14,351。可考虑在大屏继续放大角色与蛋间距，或提供可选轻量模式；这会改变观感或玩法，本次未调整。
2. **密集场景的快照复制。** 1080p 密集场景每 12 个游戏秒仍复制约 190 万个实体记录。若继续优化大群体，应保留用于测试/UI 的稳定快照，同时为渲染提供可复用缓冲，避免直接暴露可写的模拟对象。
3. **存档写入频率。** 刷新最高分时会同步写入 localStorage，连续下蛋可接近每秒五次。可合并写入并在暂停、隐藏或离开页面时刷新；当前本机未测到它成为主要瓶颈，优先级低于前两项。

后续已完成前两项，实施和验证结果见 [大屏密度与渲染缓冲](large-screens-2026-10-15.md)。

音效池、两只小猪、泥坑显示对象和皮肤纹理均有数量上限；本轮无需增加服务器逻辑或更换游戏框架。
